# 同步 FIFO 验证计划

## 1. 验证目标和当前进度

验证对象为 [`rtl/fifo.v`](../rtl/fifo.v)，预期行为见 [FIFO 设计说明](fifo_spec.md)。重点检查数据顺序、空满判断、同时读写、错误信号、复位和指针回卷。

已完成 RTL、基础 smoke 测试，以及 UVM interface、top、item、sequence、sequencer、driver、monitor、agent、env、独立 reference model 和 scoreboard 的基本实现。当前 `fifo_test` 发送单笔随机请求，monitor 逐拍采样，scoreboard 自动比较读数据、空满标志和错误信号。

目前跑通的是基本验证链路，尚未完成本文的完整用例。定向测试、功能覆盖率、SVA、参数测试和自动回归待实现。smoke 测试主要用于产生激励和查看波形，不作为完整功能验证通过的依据。

## 2. 验证平台

读写使用同一个时钟，因此使用一个 FIFO agent，同时驱动 `wr_en`、`wr_data` 和 `rd_en`。

```text
sequence -> sequencer -> driver -> fifo_if <-> DUT
                                     |
                                  monitor
                                     |
                             agent.analysis_port
                                     |
                                 scoreboard
                                     |
                              reference model
```

| 组件 | 作用 |
|---|---|
| `fifo_item` | 表示一个周期的读写使能和写数据，也可以表示空闲周期 |
| driver | 在时钟下降沿驱动信号，使其在上升沿前稳定 |
| monitor | 采集实际输入、上升沿前的空满状态和上升沿后的输出 |
| reference model | 用独立队列维护预期数据和状态，计算每拍的预期结果 |
| scoreboard | 调用 reference model，逐拍比较实际数据、空满和错误信号 |
| coverage | 记录各类测试场景是否出现 |
| SVA | 检查指针更新、输出保持和复位等行为 |

env 创建 agent 和 scoreboard，并连接采样输出。coverage 和 SVA 尚未加入；coverage 后续结合 monitor 记录与模型状态采样，SVA 检查接口和内部指针。

复位目前由 top 产生。后续扩展为统一的复位任务或组件，避免多个地方同时给 `rst` 赋值。参数测试前，所有需要位宽或深度的组件与 DUT 使用同一组配置。

### 2.1 采样时间

monitor 需要分清上升沿之前的状态和上升沿之后的结果：

| 采集内容 | 时间 |
|---|---|
| `rst`、`wr_en`、`rd_en`、`wr_data`、原来的 `full/empty` | 上升沿前 |
| `rd_data`、更新后的 `full/empty`、`wr_error/rd_error` | 本次上升沿完成寄存器更新后 |

当前已使用 clocking block：沿前信号使用 `input #1step`，沿后信号使用 `input #0`。后者在 NBA 更新后采样；它不同于普通过程中的 `#0`，不能混用。

每拍采集的数据应放在同一条 monitor 记录中。不能把本拍请求和上一拍结果比较。

待补充的异步复位处理需要单独监听 `posedge rst`，在复位赋值完成后检查输出并清空参考队列，不能等到下一个时钟沿才发现复位。可使用 `assert final` 检查复位后的值。复位与时钟沿同时发生时，按复位处理；复位前尚未处理完的采样记录不能再改变复位后的队列。初始复位也必须被模型识别。

## 3. 参考模型和 scoreboard

当前 `fifo_reference_model` 已使用 SystemVerilog queue 保存成功写入、尚未读出的数据，`fifo_expected_item` 返回预期结果，scoreboard 负责比较。当前模型固定为 8 位、深度 16；参数化后的数据声明可表示为：

```systemverilog
logic [width-1:0] expected_q[$];
logic [width-1:0] expected_rd_data;
```

用队列长度判断本拍读写应该成功还是失败，不能直接使用 DUT 的 `full/empty` 做决定，否则 DUT 标志出错时，模型也可能跟着出错。

每个非复位周期按以下顺序处理：

1. 记录操作前的队列长度，比较它与 DUT 上升沿前的 `full/empty` 是否一致。
2. 根据这个长度和采集到的使能，算出本拍是否应该读写，以及两个错误信号的期望值。
3. 如果应该读，从队首取出数据，保存到 `expected_rd_data`。
4. 如果应该写，把 `wr_data` 放到队尾。
5. 比较 `rd_data` 和 `expected_rd_data`，即使本拍没有成功读取也要比较，以检查输出保持。
6. 根据操作后的队列长度检查新的 `full/empty`，同时检查两个错误信号。

读写条件必须在修改队列之前算好。同拍读写时先取旧数据，再加入新数据。

复位时，清空队列，`expected_rd_data` 清零；复位期间不向队列添加或取出数据。还需比较稳定后的复位输出：`rd_data=0`、`full=0`、`empty=1`、两个错误信号为 0，不能只清空模型就认为复位检查通过。

实际采样字段需要保留 X/Z，比较使用 `===` 或 `!==`，发现未知值要报错；仅在比较时使用 `!==`，不能弥补前面存入 `bit` 时丢失的四态信息。

当前已统计 sample 数、比较通过次数和不匹配次数。后续补充成功写入个数、成功读出个数、复位丢弃个数，并检查：

```text
成功写入个数 = 成功读出个数 + 复位丢弃个数 + 队列剩余个数
```

完整用例结束时停止写入，按照参考队列中的剩余个数读完所有数据，等最后一次比较完成后再结束。不能只看 DUT 的 `empty` 决定是否结束，否则错误的空标志可能导致数据漏检。还应确认用例要求的有效操作实际发生，只有复位或空闲 sample 不足以证明读写测试通过。

## 4. 测试用例

用例按以下 9 组实现。同组中的子场景可以复用 sequence 和辅助任务，不要求每个检查点对应一个独立 test 类。日志中应标明正在执行的子场景，便于定位失败。

普通功能用例由 scoreboard 比较数据和接口结果，内部指针由 SVA 检查，异步复位另行检查。非法参数用例根据编译或仿真是否出现预期的参数错误判断结果。

| 用例 | 对应 Spec 章节 | 测试步骤和检查内容 |
|---|---|---|
| `tc_single_wr_rd` | 5–7 | 写入一个数据再读出，比较数据及空满标志；分别测试零值和非零值 |
| `tc_burst` | 5–7 | 连续写入后连续读出，长度分别为 1、depth−1、depth，检查顺序和每拍读写能力；从空写满时，恰好第 depth 次写入后置满；从满读空时，最后一个数据正确且读出后置空 |
| `tc_overflow_underflow` | 5–7、9、10 | 写满后连续满写至少 3 拍不同数据，检查拒绝写入、写指针保持，再读完确认原数据未覆盖；读出非零值并读空后，连续空读至少 3 拍，检查读指针和输出保持；分别检查单拍、多拍错误，以及停止请求或合法操作后错误清零；满但不写、空但不读时不报错 |
| `tc_read_timing` | 6 | 先读出一个非零值，再进行空闲、只写和空读，检查输出保持；有效读时检查本次上升沿后更新 |
| `tc_simultaneous` | 8 | 非空非满时分别保留 1 个和 depth−1 个数据，连续同拍读写至少 2*depth 拍，检查读出旧数据且数量不变，重复配置只测一次；空时检查只写成功、读输出保持、读错误置位，随后读出新数据；满时检查只读成功、full 清零、写错误置位，随后读完确认失败的写数据未进入 FIFO |
| `tc_wraparound` | 10 | 不复位，成功写和成功读各至少 6*depth 次，使两个完整指针分别回卷至少 3 次，持续比较数据 |
| `tc_reset` | 4 | 检查初始复位、空时及有数据时复位；在非时钟沿拉高复位，包含完全位于两个上升沿之间的短脉冲；分别在少量数据、已满、读输出非零、两类错误信号有效时复位；保持复位时施加四种读写组合，检查复位值保持；释放后重新写读，确认旧数据作废 |
| `tc_random` | 4–10 | 每个 seed 至少运行 1000 拍，包含四种读写组合、连续偏写、连续偏读和运行中复位，结束时读完剩余数据 |
| `tc_param_invalid` | 2 | 分别设置非法参数，检查是否因对应参数错误而停止编译或仿真 |

原 `tc_fill_to_full`、`tc_drain_to_empty` 合入 `tc_burst`；`tc_overflow`、`tc_underflow`、`tc_error_burst` 合入 `tc_overflow_underflow`；`tc_empty_wr_rd`、`tc_full_wr_rd` 合入 `tc_simultaneous`；`tc_reset_request`、`tc_mid_reset` 合入 `tc_reset`。合并只改变用例组织方式，检查内容仍需逐项完成。

连续操作指相邻时钟周期都产生请求，不能用中间插有空闲拍的请求代替。

写数据包括全 0、全 1、交替 0/1、单个 1 依次移动、递增值和随机值。所有数据按 `width` 位生成，递增值超出位宽时截断；窄位宽下允许数据重复。

## 5. SVA 检查

需要检查以下内容：

- 复位后指针、读输出和错误信号为 0，`empty=1`、`full=0`。
- 正常工作时，`full` 和 `empty` 不同时为 1，输出没有 X/Z。
- 成功写入时，写指针加 1；其他情况下保持。
- 成功读取时，读指针加 1；其他情况下保持。
- 没有成功读取且没有复位时，`rd_data` 保持。
- 两个错误信号符合 Spec 第 9 节，不能少报、多报或晚一拍。
- 地址回到 0 时，指针最高位翻转；整个指针溢出后回到 0。

并发断言在时钟沿采样到的是寄存器更新前的值。可以使用 `|=>` 和 `$past()` 检查前一次上升沿的操作结果，指针加法按实际位宽计算。使用 `$past()` 前要确认已有有效的历史采样。

普通时钟断言在复位期间用 `disable iff (rst)` 禁用，异步复位另行检查。还要记录关键断言的触发条件是否出现，避免用例没有产生相应操作却被认为验证完成。

## 6. 功能覆盖率

使用参考队列中的数据个数统计空、非空非满、满三种状态。每个表项都需要在测试中出现并通过检查。

| 覆盖内容 | 需要出现的情况 |
|---|---|
| 状态和请求组合 | 三种状态分别与不读不写、只写、只读、同时读写组合，共 12 种 |
| 数据个数 | 0 到 depth 的每个值 |
| 空满变化 | 0→1、1→0、depth−1→depth、depth→depth−1；depth=2 时合并重复项 |
| 同时读写 | 空、满、非空非满时分别测试 |
| 输出保持 | 读输出非零时，分别进行空闲、只写、空读 |
| 错误信号 | 写错误和读错误分别出现 0→1、1→1、1→0 |
| 指针回卷 | 读写地址回卷和完整指针回卷，次数满足 `tc_wraparound` 要求 |
| 复位 | 初始复位、空时复位、有数据时复位、满时复位、错误信号有效时复位、两个上升沿之间的短复位 |
| 连续操作 | 成功操作持续 1 拍、2 到 depth 拍、超过 depth 拍；长时间连续读写在非空非满状态下进行 |
| 数据 | 第 4 节的数据类型均成功写入并读出，每个数据位都出现过 0 和 1 |

每种参数配置单独统计。数据个数使用 0 到 depth 的独立 bins，避免 depth=2 时区间重叠。两个错误信号同时为 1 不属于正常可达情况，不要求覆盖。

以上功能覆盖项要求全部完成。没有覆盖的项目应说明原因，确认是需要补充测试还是确实不适用。代码覆盖率用于辅助发现遗漏，还需检查未覆盖的代码行、分支和信号翻转。

## 7. 参数测试

参数测试分阶段开展：

1. 先使用默认 `(width, depth)=(8,16)` 完成定向用例，再用少量固定 seeds 调试随机测试。
2. 参数配置统一后，先增加 `(8,2)`、`(1,16)`、`(32,16)`，检查最小深度、单 bit 和宽数据。
3. 完整回归覆盖下表全部配置。每组运行全部定向用例，随机测试按表中 seed 数作为起始目标；根据覆盖率和失败情况继续补充，不以 seed 数量代替功能检查。

| width | depth | 测试目的 | 完整回归随机 seed 数 |
|---:|---:|---|---:|
| 8 | 16 | 默认配置 | 20 |
| 8 | 2 | 最小深度 | 10 |
| 8 | 4 | 小深度 | 10 |
| 8 | 8 | 中等深度 | 5 |
| 8 | 32 | 较大深度 | 5 |
| 1 | 16 | 单 bit 数据 | 5 |
| 32 | 16 | 宽数据 | 10 |
| 1 | 2 | 最小位宽和最小深度组合 | 5 |

非法配置分别为 `(width, depth)=(0,16)、(-1,16)、(8,0)、(8,1)、(8,-1)、(8,3)、(8,6)、(8,12)`。

非法参数测试使用只实例化 DUT 的简单顶层，避免 UVM 组件先因为参数出错。能够完成编译的配置，应在仿真开始时出现对应 `$fatal` 信息；编译阶段就失败的配置，应确认错误来自 DUT 的非法参数。许可证、缺少文件、超时等问题不能算测试通过。

## 8. 回归和通过条件

后续在 `sim/Makefile` 和 `sim/regress.py` 中实现编译、运行和汇总。先支持默认参数的定向测试，再加入多 seed 和多参数配置。每次运行保存 testcase、子场景、参数、seed、代码版本、工具版本、日志和结果，失败时能够用相同配置重现。

完整回归中，普通测试通过需要同时满足：

- 编译和仿真正常完成，没有超时。
- monitor 确实采集到了数据，必要的测试操作和比较实际执行。
- scoreboard 没有数据、状态或错误信号不匹配。
- UVM error/fatal 和断言失败均为 0。
- 剩余数据已读完，读写统计正确。

开发阶段可以先运行部分用例，但未实现的断言、复位检查或统计项应明确列为待完成，不能因为没有报错就认定这些检查已经通过。

非法参数测试单独判断是否按预期报错。回归脚本不能只看仿真退出码，也要检查完成标记和错误信息；任意普通测试失败或非法参数未按预期报错，回归返回非零退出码。

## 9. 故意修改 RTL，检查测试能否发现错误

在 RTL 副本上每次只修改一处，先确认原始版本通过，再运行修改后的版本。普通功能错误应由数据比较或断言发现，编译失败和超时不算发现了功能错误。删除参数合法性检查这一项，单独由非法参数测试判断。

先验证读错地址、错误信号计算错误和复位未清指针三类修改，跑通执行与报错记录流程，再补齐下表其余项目。

| 修改内容 | 应该发现问题的测试 |
|---|---|
| full 判断删掉最高位比较 | `tc_burst` 的写满和读空子场景 |
| 满写时仍移动写指针 | `tc_overflow_underflow`、指针断言 |
| 满写时仍写 RAM | `tc_overflow_underflow` 的满写后读完并比较 |
| 空读时清零 rd_data | `tc_overflow_underflow`、`tc_read_timing` |
| 读取下一个地址 | `tc_single_wr_rd`、`tc_burst` |
| wr_error 直接等于 full | `tc_overflow_underflow` 的满但不写子场景 |
| rd_error 直接等于 empty | `tc_overflow_underflow` 的空但不读子场景 |
| 复位时不清指针 | `tc_reset` 的有数据时复位子场景 |
| 写指针每次加 2 | `tc_burst`、指针断言 |
| 删除 depth 为 2 的幂检查 | `tc_param_invalid` 的 depth=6 配置 |

每项记录修改内容、运行用例和具体报错。没有发现问题时，补充测试或检查逻辑后重跑。

## 10. 完成标准

阶段性完成按以下范围记录：

- 基本链路跑通：请求经过 driver 驱动，monitor 发送采样，reference model 和 scoreboard 执行比较。目前处于这一阶段。
- 默认配置功能测试完成：第 4 节默认配置下的全部定向子场景通过，相关连续驱动、复位处理和结束检查已补齐；指针检查需有 SVA 结果。
- 完整验证完成：满足以下全部条件。

- Spec 中的功能均有对应测试，所有计划用例已实现并通过。
- 合法参数配置和指定随机 seeds 全部通过，非法参数按预期报错。
- 数据比较、UVM 和断言没有未解决的错误。
- 功能覆盖项全部完成，不适用的项目有明确说明。
- 第 9 节的十种错误都能被测试发现。
- 可以用一条已写入使用说明的命令运行回归并汇总结果。

本项目不验证双时钟传输、RAM 宏或物理时序等 Spec 未包含的内容。
